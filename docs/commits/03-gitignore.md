## 1. Objective

The objective of this commit is to create a root-level `.gitignore` file for **Fix-My-Ride** so that generated artifacts, installed dependencies, local editor settings, temporary files, and sensitive environment variables are never accidentally committed to the Git repository.

---

## 2. What is Git?

**Git** is a distributed version control system that tracks changes to your project files over time. Think of it like a detailed history logbook for your codebase:

- Every time you make a **commit**, Git takes a snapshot of the project files you chose to track.
- You can look back at previous versions, compare changes line by line, collaborate with other developers without overwriting each other's work, and safely undo mistakes.

However, Git works best when it tracks **source files** (the human-written code, configurations, and documentation that define your application), not every temporary or machine-generated file created while running the project.

---

## 3. What is `.gitignore`?

A **`.gitignore`** file is a plain text configuration file placed in a Git repository (usually at the project root) that tells Git which files and folders it should completely ignore.

When a file or folder matches a rule inside `.gitignore`:

- Git does **not** show it as an untracked file in `git status`.
- Git does **not** include it when you run `git add .`.
- Git leaves it untouched on your local computer so your tools can still use it normally.

### Practical Example: Tracked vs. Ignored Files

| File / Folder | Status in Git | Why? |
| :--- | :--- | :--- |
| `README.md` | **Tracked** | Core project documentation that every developer needs. |
| `frontend/src/App.jsx` *(future)* | **Tracked** | Human-written React source code that defines the UI. |
| `backend/app/main.py` *(future)* | **Tracked** | Human-written FastAPI source code that runs the API. |
| `.env.example` *(future)* | **Tracked** | Safe template showing which environment variables are required. |
| `frontend/node_modules/` | **Ignored** | Thousands of downloadable third-party JS packages installed by `npm`. |
| `backend/.venv/` | **Ignored** | Local Python virtual environment specific to your machine. |
| `backend/__pycache__/main.cpython-312.pyc` | **Ignored** | Auto-generated Python bytecode compiled when running code. |
| `.env` | **Ignored** | Contains real passwords, database URLs, and API secrets. |

## 4. Why Should We Ignore Certain Files?

Ignoring non-source files keeps the repository clean, secure, and reliable:

1. **Security (Protecting Secrets):**  
   Database passwords, PostgreSQL connection strings, JWT signing keys, and API tokens live in `.env` files. Committing them—even once—exposes sensitive credentials in Git history.
2. **Smaller and Faster Repository:**  
   Folders like `node_modules/` or `.venv/` can contain tens of thousands of files and hundreds of megabytes. Everyone can recreate them locally from `package.json` or `requirements.txt`, so storing them in Git wastes space and slows down cloning and pulling.
3. **No Machine-Specific Conflicts:**  
   Your local OS (`.DS_Store` on macOS, `Thumbs.db` on Windows) and your personal IDE settings (`.vscode/`, `.idea/`) differ from teammate to teammate. Ignoring them prevents noisy merge conflicts over personal preferences.
4. **Clean Code Reviews and Diffs:**  
   Ignoring build outputs (`dist/`, `build/`), caches (`__pycache__/`, `.pytest_cache/`), and log files (`*.log`) ensures pull requests only contain meaningful changes to source code and documentation.

## 5. Explanation of Each Ignore Category

The root `.gitignore` organizes rules into six clear categories tailored to the **Fix-My-Ride** stack (React + Vite + Material UI + Axios on the frontend, Python + FastAPI + SQLAlchemy + PostgreSQL on the backend):

### Node.js and React (Frontend)

- `node_modules/` — All JavaScript packages downloaded by npm/yarn/pnpm. Recreated anytime with `npm install`.
- `dist/` — Production bundle output generated by Vite (`npm run build`).
- `build/` — Alternative build output folder used by Node/React tooling.
- `npm-debug.log*`, `yarn-debug.log*`, `pnpm-debug.log*` — Error log files generated when a package manager command fails.

### Python (Backend)

- `__pycache__/`, `*.py[cod]`, `*.pyo` — Compiled Python bytecode (`.pyc`, `.pyo`, `.pyd`) automatically created by the Python interpreter to speed up imports.
- `.Python` — Symlink or marker created inside certain Python virtual environments.
- `venv/`, `.venv/`, `env/`, `ENV/` — Local Python virtual environment directories holding installed packages like FastAPI and SQLAlchemy.
- `*.egg-info/` — Packaging metadata generated when installing local Python packages in editable or distribution mode.
- `.pytest_cache/`, `.mypy_cache/` — Local cache folders generated by `pytest` (testing) and `mypy` (type checking).

### Environment Variables and Secrets

- `.env` — Primary local environment file containing sensitive runtime configuration (e.g., PostgreSQL credentials).
- `.env.*` — Environment-specific files such as `.env.local`, `.env.development`, or `.env.production` that may hold local overrides or secrets.
- `!.env.example` — An **exception rule** (the leading `!` negates the `.env.*` rule above it) so sample environment template files remain trackable in Git.

### IDE and Editor Files

- `.idea/` — Project metadata and local workspace settings created by JetBrains IDEs (such as PyCharm or WebStorm).
- `.vscode/` — Local editor preferences and workspace state created by Visual Studio Code.

*(Note: Keeping these directory rules targeted ensures shared project files like `README.md`, documentation, and future source files remain completely unaffected.)*

### Operating System Files

- `.DS_Store` — Hidden folder-view metadata file automatically created by macOS Finder.
- `Thumbs.db` — Thumbnail cache file created by Windows Explorer.
- `Desktop.ini` — Folder customization file created by Windows.

### Logs and Temporary Files

- `*.log` — Application, server, or database runtime log files.
- `*.tmp` — Temporary scratch files written by editors or tools.
- `*.bak` — Backup copies automatically saved by text editors or utilities.

## 6. Why `.env.example` Should Not Be Ignored

While real `.env` files must stay secret and out of Git, a **`.env.example`** file serves a different purpose:

- It lists the **names** of required environment variables (for example, `DATABASE_URL=postgresql://user:password@localhost:5432/fix_my_ride`) using harmless placeholder values instead of real secrets.
- When a new developer clones the repository, they copy `.env.example` to `.env` and fill in their own local PostgreSQL username, password, and settings.
- If `.env.example` were ignored by `.env.*`, teammates would have no documented list of required configuration keys. Adding `!.env.example` right after `.env.*` ensures the template stays tracked while real secrets stay ignored.

## 8. How to Verify Git Ignore Rules

You can test `.gitignore` rules directly from the project root using `git check-ignore -v`. The `-v` (verbose) flag prints the exact file and line number of the rule that matched.

> **Tip:** `git check-ignore` evaluates patterns against the path strings you pass to it—**the files or folders do not even need to exist on disk yet!** This makes it easy to verify rules before installing dependencies or creating virtual environments.

Run the following commands from the repository root:

```bash
git check-ignore -v frontend/node_modules/example
git check-ignore -v frontend/dist/example
git check-ignore -v backend/__pycache__/example.pyc
git check-ignore -v backend/.venv/example
git check-ignore -v .env
```

Next, verify that `.env.example` is **not** ignored:

```bash
git check-ignore -v .env.example
git check-ignore .env.example
```

Finally, inspect the repository status to confirm existing tracked files (`README.md`, `frontend/README.md`, `backend/README.md`, and `docs/commits/`) are unaffected:

```bash
git status
```
