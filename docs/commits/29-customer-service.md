## 2. What a Service Layer Is

A **service layer** is the middle layer of Python functions that performs real business and database work—creating records, checking rules, and querying tables—using a SQLAlchemy `Session`, without knowing anything about HTTP URLs, status codes, or FastAPI requests.

---

## 3. Why Business Operations Should Be Separated from API Routes

- **Clean, readable routes:** Future route handlers stay short—they receive an HTTP request, call `create_customer(db, customer_data)`, and return the result.
- **Reusability:** Both an HTTP endpoint and a background script or CLI test can call the exact same `get_customer_by_phone()` function.
- **Easier testing:** You can test service functions directly against PostgreSQL using a `Session`, independent of HTTP routing.

## 5. What SQLAlchemy `Session` Means

A **`Session`** (type `sqlalchemy.orm.Session`) is an active workspace talking to PostgreSQL. It tracks new or modified ORM objects in memory, sends SQL commands inside a transaction, and commits or rolls back changes cleanly.

---

## 6. How `create_customer()` Works

```python
def create_customer(db: Session, customer_data: CustomerCreate) -> Customer:
    customer = Customer(**customer_data.model_dump())
    db.add(customer)
    try:
        db.commit()
        db.refresh(customer)
        return customer
    except IntegrityError as exc:
        db.rollback()
        ...
```

Step by step:

1. Receives `db: Session` and validated `customer_data: CustomerCreate`.
2. Converts `CustomerCreate` to a dictionary with `.model_dump()` (Pydantic 2.x).
3. Instantiates `Customer(...)` and stages it with `db.add(customer)`.
4. Commits with `db.commit()` and reloads database-generated fields (`id`, `created_at`, `updated_at`) with `db.refresh(customer)`.
5. Returns the `Customer` ORM model instance.

---

## 7. How `db.add()` Works

`db.add(customer)` places the new `Customer` object into the session's pending list. At this moment, **nothing has been saved to PostgreSQL yet**—the object is simply staged for the upcoming commit.

---

## 8. How `db.commit()` Works

`db.commit()` flushes pending SQL (`INSERT INTO customers ...`) to PostgreSQL and permanently commits the database transaction. PostgreSQL validates constraints (like `UNIQUE` on `phone_number` and `email`) and generates `id`, `created_at`, and `updated_at`.

---

## 9. How `db.refresh()` Works

Right after `db.commit()`, the Python `customer` object still needs the `id`, `created_at`, and `updated_at` values generated by PostgreSQL (`nextval` and `now()`). Calling `db.refresh(customer)` runs a `SELECT` on that row so all database-generated fields are immediately populated on the returned `Customer` object.

---

## 10. Why `rollback` Is Necessary

If `db.commit()` fails (for example, because a duplicate `phone_number` violates PostgreSQL's unique constraint), PostgreSQL marks the current transaction as aborted. Until `db.rollback()` runs, **any further query on that `Session` will fail**. Calling `db.rollback()` inside `except` resets the session cleanly so it remains usable.

---

## 11. How `get_customer_by_id()` Works

Queries PostgreSQL by primary key:

```python
statement = select(Customer).where(Customer.id == customer_id)
return db.scalar(statement)
```

Returns the `Customer` instance if found, or `None` if no matching row exists—never raising `HTTPException` inside the service layer.

---

## 12. How `get_customer_by_phone()` Works

Queries PostgreSQL by unique `phone_number`:

```python
statement = select(Customer).where(Customer.phone_number == phone_number)
return db.scalar(statement)
```

Returns `Customer` or `None`.

---

## 13. How `get_customers()` Works

Queries all customers ordered ascending by `id` for deterministic output:

```python
statement = select(Customer).order_by(Customer.id.asc())
return list(db.scalars(statement).all())
```

*(Pagination is intentionally left out of Commit 29.)*

---

## 14. SQLAlchemy 2.x Querying Conventions

Notice that all read queries use modern SQLAlchemy 2.x `select(Customer)` statements executed with `db.scalar(...)` / `db.scalars(...)` rather than legacy SQLAlchemy 1.x `db.query(Customer)` syntax. Read operations do **not** call `db.commit()`.

---

## 15. Difference Between Returning ORM Models and Pydantic Schemas

`customer_service.py` returns **`Customer` ORM model instances** (not `CustomerResponse`). That keeps the service reusable across internal backend operations, while future FastAPI route handlers (configured with `response_model=CustomerResponse` and `from_attributes=True`) handle JSON serialization at the HTTP boundary.

---

## 16. Database Integrity Errors Explained

When a caller tries to insert a duplicate `phone_number` or `email`, PostgreSQL raises a `UniqueViolation` wrapped by SQLAlchemy as **`IntegrityError`**. `create_customer()` catches `IntegrityError`, calls `db.rollback()`, translates duplicate `phone_number`/`email` constraints into a clear `ValueError` (preserving the original cause via `from exc`), and re-raises unexpected database errors after rolling back.
